## 观察

以下是**数字**：

1. 「仅账号层」的 actor F1 = 1.000，与「全量」相同；但团伙数是 **0**。
2. 「仅协同层」的团伙数是 **3**，与「全量」相同；但 actor 召回只有 **0.725**。
3. 三个团伙的平均纯度是 **1.000**，即报出来的成员全部是注入的水军账号。
4. item 级召回在所有含文本层的组合里都是 **0.096**，与是否加协同层无关。
5. 「仅文本层」的 actor F1 = 0，但它有 item P = 1.000。

以下是**解释**（可能是错的）：

- 观察 1 与 2 合起来说明三层不是冗余：「发现团伙」和「把账号判准」是两种
  不同的能力，各自有独立的层承载。→ 对应文档里的 E1。
- 观察 3 说明协同层的三个信号都没有乱抓：`cluster` 抓到的 8 个、`cooccur`
  抓到的 6 个、`burst` 抓到的 15 个，都是注入的账号。
- 观察 4 是我的**推断**：协同层的证据长在团伙上，不传播到具体条目，
  所以加不加协同层都不改变 item 级召回。→ 对应 D13 与 README 的迭代清单第 1 项。
- 观察 5 说明文本层「precision 高、recall 低」：它只认话术和正则，
  没说过话术的正常水军它抓不到。这符合设计预期，不是缺陷。

## 结论

1. 三层互补性成立，可以进 README。**但只在合成数据上成立**（见 H1）。
2. 团伙纯度 100%，说明协同层当前的阈值设置没有引入误报 ——
   代价是可能漏报（没有对照组可以验证漏了多少）。
3. item 级召回 0.096 需要在 README 里**主动解释**，而不是藏起来。
   它是定位问题（证据在团伙层，指标在条目层），不是算法问题。
4. 性能热点只有 `coordination.cluster` 一个（422ms / 总 497ms），
   与架构文档第 5 节的复杂度分析一致。
