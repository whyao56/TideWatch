# 架构说明

这份文档讲两件事：**数据怎么流**，以及**为什么这样切模块**。
信号本身的原理不在这里 —— 那是每个信号类里的 `principle` 字段，
用 `tidewatch signals` 就能打出来，代码改了原理说明不可能忘。

---

## 1. 一句话概括

> 引擎只认识一个对象（`Dataset`），只做一件事（把信号聚合成分级结论），
> 其余全部是可替换的外围。

这个约束是刻意设计的。它带来三个可验证的性质：

- **换数据源不用改引擎** —— 差异全在 `adapters/` 里被消化
- **加信号不用改已有代码** —— 新信号只碰注册表，不碰聚合器
- **调参数不用改代码** —— 所有会变的数值都在 YAML 里，且可被命令行临时覆盖

---

## 2. 数据流

```
原始记录 (dict)                                    adapters/base.py
  │  dig() 按点路径取值                             ├─ FieldMap：字段映射（纯数据）
  │  parse_time() 统一时间                          └─ MappedAdapter：边读边转
  ▼
Item / Actor                                       types.py
  │  平台无关：不含任何 aid / oid / mid 之类的字段
  ▼
Dataset                                            types.py
  │  by_topic() / by_actor() / time_span
  ├──────────────────┬──────────────────┬──────────────────────┐
  ▼                  ▼                  ▼                      │
ItemSignal         ActorSignal      CoordinationSignal         │  signals/
（逐条）            （逐账号）         （整批）                    │
  │                  │                  │                      │
  └──────────────────┴──────────────────┘                      │
                     ▼                                          │
              list[SignalHit]                                   │
              （信号只回答「我看到了什么」，不做加权）              │
                     ▼                                          │
              Scorer.assess()          ── 加权 → 跨层联动 → 封顶 → 切档
                     ▼                                          │
              list[Assessment]                                  │
                     ▼                                          │
        propagate_group_members()  ── 团伙 → 成员的二级传播        │
                     ▼                                          │
              重新 assess()  ── 成员带上打折后的协同证据            │
                     ▼                                          │
     report.py: render_text / render_json / render_markdown    ──┘
```

### 关键的一次「折返」

注意流水线里有一次**反向**的步骤：评分完 → 传播 → 再评分。

原因是协同层产出的目标是**团伙**（GROUP），而使用者拿到报告后第一个问题
一定是「那具体是哪些账号」。所以团伙的可疑度要按系数传给它的成员账号，
成员分数变了，就得重新聚合一次。

这次折返带来两条必须遵守的规则（`scoring.py` 里写了原因）：

- 传播过去的证据一律标 `WEAK` —— 团伙一旦误报会连坐全体成员
- 传播是**追加**而不是覆盖 —— 否则一个「老账号 + 资料正常」的团伙成员，
  会因为它原本没有负面信号而被传播分从零算起

## 3. 模块边界与职责

| 模块 | 职责 | 明确**不做**的事 |
|---|---|---|
| `types.py` | 定义平台无关的数据模型 | 不认识任何平台字段 |
| `matching.py` | AC 自动机（多模式串匹配） | 不知道匹配到的词意味着什么 |
| `text.py` | 归一化、折叠、分词、统计量 | 不做任何判定，全是纯函数 |
| `rules.py` | 加载/缓存规则库 | 不决定规则怎么用 |
| `signals/` | 判定逻辑（唯一的扩展点） | 不算总分，不做加权 |
| `scoring.py` | 把命中聚合成分级结论 | 不知道任何具体信号的含义 |
| `pipeline.py` | 编排与计时 | **不含任何判定逻辑** |
| `report.py` | 渲染成人读/机读 | 不做任何计算 |
| `adapters/` | 把外部数据变成 `Dataset` | 不做任何判定 |
| `cli.py` | 参数解析与输出 | 不做任何判定 |
| `eval/` | 指标与消融实验 | 不参与运行时 |

三条边界值得单独解释，因为它们都曾经被违反过：

### 为什么 `pipeline.py` 必须很薄

流水线只做编排和计时，一个 `if` 都不做判定。原因是：**调一条判定规则不该
改动流水线**。否则每次实验都会引入无关的代码差异，对照实验就失去意义
（你没法确定结果变化是来自参数，还是来自你顺手改的那一行）。

### 为什么信号不回答「总共多少分」

`SignalHit.score` 是 **[0, 1] 的强度**，不是最终分数。加权、跨层联动、封顶
全部由聚合器负责。

这条边界的价值在于：**加一个新信号永远不会扰动已有信号的表现**。
如果允许多个信号各自决定自己的绝对分值，那么调一个信号的权重就会连带
影响所有实验结论 —— 对照实验就没法做了。

### 为什么 `text.py` 里全是纯函数、不依赖 numpy

这些函数是可单测的，也可以被直接拷进别的项目用 —— 这本身就是「可微调」
的一种形态。少一个依赖，别人的采用成本就低一截。

## 4. 三层为什么这么分

分层的依据不是「数据来源不同」，而是**可信度与规避成本递增**：

| 层 | 判定单位 | 规避成本 | 层权重 | 单独定案？ |
|---|---|---|---|---|
| 文本层 | 单条发言 | 极低（换个说法就行） | 0.9 | 可以（话术类） |
| 账号层 | 单个账号 | 低（买个老号） | 0.7 | **绝不** |
| 协同层 | 团伙 | **高**（要放弃协同本身） | 1.3 | 可以 |

这个顺序决定了三件事：

1. **层权重必须递增。** 越难伪造的证据越值钱。反过来配权重的话，
   引擎会被最便宜的信号主导，也就是被对手最容易操纵的那一层主导。
2. **账号层永远不单独定案。** 它全是弱信号（新号、无头像、默认昵称），
   这些特征单独看毫无意义 —— 每天有大量正常用户注册。
   所以这一层的每个信号都刻意把强度压得很低，必须多个叠加才触发
   （`account.profile` 是 0.3 + 0.2 + 0.3 + 0.2 的加权和，低于 0.4 不报）。
3. **协同层必须校验跨账号。** 一个人连发十八条是**刷屏**，
   属于账号层的原创度问题，不是「一群人一起行动」。
   `burst` 和 `cluster` 都有 `min_actors` 校验，缺了它
   任何活跃用户都能把自己刷成「爆发团伙」。

## 5. 复杂度与性能

实测（193 条发言 / 160 账号 / 10 话题，单机 Python 3.13）：

| 信号 | 耗时 | 复杂度 | 备注 |
|---|---|---|---|
| `coordination.cluster` | ~420 ms | O(n²) 同话题内两两比较 | 唯一的热点 |
| `text.template` | ~12 ms | O(n × 词数) | |
| `text.repetition` | ~5 ms | O(n × 文本长) | |
| `text.evasion` | ~4 ms | O(n × 文本长) | 两次 AC 匹配 |
| 其余 6 个信号合计 | < 5 ms | | |
| 评分 + 传播 + 重评 | ~2 ms | O(命中数) | |

热点只有一处：**文本聚类的同话题两两比较**。

它的两级过滤就是为此设计的：

```
第一级 SimHash 汉明距离   O(1)  → 排除绝大多数不相关的对
第二级 最长公共子串比例    O(nm) → 只对活下来的对做精确确认
```

只用第一级会漏掉「局部照抄」（改了前半段、原样保留后半段）；
只用第二级则慢到无法接受。两级串起来，既便宜又不漏。

**已知的性能天花板**（见 README「已知限制」）：

- `_MAX_PER_TOPIC = 400`：单话题超过 400 条只取前 400 条
- 共现图 `O(账号数²)`：账号上万时需要先按活跃度剪枝
- 真正的解法是 SimHash 分桶 + LSH 索引，这是迭代清单里的一项

## 6. 扩展点

整个引擎只有**三个**扩展点，都是有意的：

```
1. 规则库      rules/*.yaml        改数据     —— 最常用，不需要读懂代码
2. 字段映射    adapters/FieldMap   改接入     —— 纯数据，不需要写代码
3. 新信号      signals/ + @register 改逻辑    —— 唯一需要写代码的地方
```

三者的共同约束是：**加东西不该改动已有代码**。任何需要改聚合器、
改报告、改流水线才能加进来的东西，都说明抽象漏了。

新信号加完有两件事必须做，否则不算完成：

1. 在 `configs/default.yaml` 里给它一段配置，**并且带上 `enabled` 开关**。
   没有开关的信号别人没法一键消融，也就没法验证它到底有没有用。
2. 跑 `tidewatch signals` 确认它能被列出来 —— `test_all_signals_exposed_via_config`
   会检查「配置里声明的」和「代码里注册的」是否完全一致，
   防止配置改了名字而代码没跟上这类静默失配。

## 7. 目录约定

```
configs/     配置（唯一放可调参数的地方，其他地方不许出现魔法数字）
rules/       规则库（纯数据，改这里不需要读懂 Python）
data/raw/    原始数据，不进版本库（可能含个人信息）
data/sample/ 样例数据，进版本库（review 时要能看到数据长什么样）
data/eval/   带标注的合成数据，进版本库（评测可复现）
out/         检测产物，不进版本库（可重跑生成）
experiments/ 实验记录（时间戳 + 配置指纹 + 观察，见该目录的 README）
docs/        文档；benchmark.md 是自动生成的，不要手工改
```
